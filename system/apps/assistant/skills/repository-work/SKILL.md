GitHub workflow: For all GitHub-related project work in this assistant, find the owning Git checkout and verify its remote before editing. Work in the repository first and keep applicable installed files, installer payload, dependencies, documentation and tests synchronized during the task. For Enclosure integrations, check ~/rebos_enclosure first, then ~/code/rebos_enclosure and resolved installed symlink targets; verify the owning checkout with git rev-parse --show-toplevel and git remote -v, then read its AGENTS.md. Installed copies may live under ~/.local/share/enclosure without .git; a missing .git there does not mean the project has no repository. Map assistant to system/apps/assistant, shell to system/apps/shell and media to system/apps/media. Before finishing, compare task-related installed files with tracked source and recover any missed focused changes into the checkout. Ask only when a new repository's destination or visibility is unclear. Never force-push, include secrets or personal state, or bypass sandbox approvals. Do not push automatically. Push only when the user explicitly requests it or uses the Push button in GitHub Settings. Report verification and the local commit; clearly state when changes have not been pushed. Create releases when requested.

## Local commits

- Group the work by user-visible intent. Default to one local commit for a coherent, verified task. Keep implementation, tests, documentation, and required generated files together when they support the same change. Split only independently useful changes that can each be verified and reverted on their own. Fold iteration and verification fixes into the task before committing.
- Check branch and PR policy, worktree status, and the index. Stage explicit task paths or hunks and review the exact staged diff. Preserve unrelated staged and unstaged work, including changes in shared files. If the task's changes cannot be isolated confidently, leave them uncommitted and report the blocker.
- Run a focused check that exercises the expected behavior. Then automatically commit the verified task changes locally in the verified checkout. Skip empty commits and leave unverified changes uncommitted when a required check is blocked or fails.
- Follow the repository's commit-message convention. Otherwise use a short imperative subject that names what changed, such as `Keep the lyrics progress track still during playback`. Add a body when the reason or tradeoff would help a future reader. Report the commit hash, verification, and push status.

GitHub network access: Dweebo enables network access in Codex workspace mode while retaining workspace file protections and tool approvals. Try the normal git or gh command first. Host or administrator restrictions can still block access. For GitHub DNS failures (Could not resolve host), blocked connections, or a gh auth status failure in that sandbox, request the execution tool's supported network approval for the exact git or gh command and retry after approval. For Codex exec_command use sandbox_permissions=require_escalated with a specific justification when that option is available. Task authorization to push does not replace a tool approval. If approval is unavailable or rejected, report the exact blocker and give the user the command to run. A sandboxed gh auth status failure does not establish an invalid credential. Never log out, delete credentials, or start reauthentication based on that failure; verify authentication only after network access succeeds.
